# 工程与文档维护

目标是让开发始终有序，Agent 从简短索引读到当前事实。清理是每次变更的完成条件，定时任务是补充。定期运行由 Codex app 的“维护 Munie 工程与文档”自动化调度；实际触发状态以 app 为准，不把文档描述当后台服务。

## 唯一来源

| 问题 | 唯一权威位置 |
|---|---|
| 用户到底要什么、优先级与验收 | [需求](requirements.md) |
| 现在实现/验证/阻塞是什么、下一步 | [项目状态](project-status.md) |
| 已实现代码与数据所有权 | [架构](architecture.md) |
| 为什么作出长期选择、未来边界 | [决策索引](decisions/README.md) |
| 日常工程、代码、性能、平台体验规则 | [标准索引](standards/README.md) |
| 调研来源、固定版本、许可、采用决定 | [引用索引](../references/README.md) |
| 价值假设和实验方法 | [产品验证](product.md) |

其他文档链接权威位置，不再维护第二份需求、状态或规则。README 只提供真实简介和导航，agent 索引只路由。文档使用语义主题名，不使用 `0001-` 等数字前缀；目录 README 是入口。研究归档保留来源与日期，清楚标为历史，不作为执行指令。

## 随变更维护

需求改变时先改需求，再按影响同步设计、任务和测试；实现变化更新架构，实际执行后更新状态。移动/合并文档同时修复全部维护链接，删除被替代的文档，历史由 Git 保存。新专题必须从索引可达；重复段落归并到唯一来源。

`python3 scripts/check-repository.py` 验证维护链接、文档无数字前缀、所有 docs Markdown 可从文档入口找到，以及工程契约。自动检查无法判断语义过时或内容重复，Agent 仍需对照真实代码、PR 与运行结果复核。需求/任务卡/PR 只有改变时更新，禁止为了维护而制造无效提交。

## 定期整理与安全边界

每日检查状态、未完成 PR、文档索引/引用、重复或过期规则、生成物和已合并分支。先检查 git status/worktree，复用已有维护工作；只清理可明确识别且不再需要的项目产物及干净、已合并 feature worktree。改动按工程契约走验证、复核和受保护 PR 集成，不直接推 main/dev。

保留用户数据、未提交工作、仍需诊断的日志、参考源码和许可证。不能以“垃圾清理”为由执行全仓 `git clean -fdx`、重置未知改动或删除研究依据；不能安全区分时保留并记录具体原因。清理前列出对象与依据，清理后验证引用、构建和工作区状态。摘要只报告实际变更/执行与剩余事项，不宣称没人运行的后台维护已经完成。
