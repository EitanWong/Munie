# App-managed away connection / App 管理的离家连接

Status: loopback-only development pilot with a guarded Mac worker adapter and a Debug simulator iPhone client. Not enabled by either shipping app or any deployed relay listener.

## Decision

Keep explicit nearby confirmation as the only enrollment path. Reuse the [adopted Remodex implementation](../../references/remodex-adoption.md), its existing device keys and the v2 encrypted task channel. Do not publish the local relay or its pairing-code, push, or account control routes. Application encryption does not make a relay connection eligible to take over a route.

For a pilot, the Mac app should opt in to one fixed Munie HTTPS/WSS origin and initiate an outbound connection; the operator enrolls the Mac's public key. The hosted service should accept only authenticated reconnects from the phone already approved on that Mac. Keep LAN and WAN as separate route hints for the same pinned identity, with one bridge and one active telephone route. Changing paths must not create a second Codex runtime or resend an unconfirmed task. Failure to reach an endpoint permits fallback for the same Mac; invalid identity or authoritative revocation does not. Commit a route only after the existing v2 handshake and initialization succeed.

## Prototype and deployment gates

The [admission module](../../apps/MunieRemodexRelay/managed-admission.js) uses Node's standard Ed25519 APIs and no new dependency. Its one-use, 15-second challenge binds the audience, role, exact public keys, nonce and registration generation. Registrations are bounded by a configured pilot allowlist and pending challenges by a fixed capacity. Additionally, each allowlisted Mac can receive at most 16 challenges per role in a rolling 15-second service-clock window. Issuing, not verifying a proof, spends a slot; rotation, deactivation or proof consumption does not restore it. A replacement or deactivation invalidates old proofs; generation checks let the listener reject a stale callback. This in-memory module does not open a port, provision keys, close sockets, or carry task data.

The separate [loopback pilot](../../apps/MunieRemodexRelay/managed-relay-pilot.js) accepts challenges and WebSocket connections on an ephemeral `127.0.0.1` port, using only generated fixture keys in tests. It verifies and consumes the proof before the upgrade but commits the registration in the successful upgrade callback. A competing phone does not replace the active phone. Mac output is scoped to the active phone route ID; queued output for a departed phone is dropped. An absent phone is not a Mac disconnect: the pilot reports a dropped frame via a control ping and neither buffers nor replays it. The HTTP `101` response alone is not authenticated readiness: app integration must wait for the end-to-end handshake and initialization.

The [Mac worker adapter](../../apps/MunieRemodexBridge/src/managed-relay-client.js) starts only with an explicit developer loopback origin not forwarded by the signed app launcher. It reuses the existing locally stored Mac key and the single trusted phone, with no new user credential and no second app-server process. The local relay admits only one LAN or managed route at a time. A provisional route expires if it does not reach v2 resume within 25 seconds. Disconnect advances the route boundary, clears old transport keys, and preserves replay history for a newly authenticated handshake. Correlated replies are not replayed and cannot cross secure sessions; oversized replies return a typed error, and oversized buffered events request canonical history refresh. Replacing the trusted phone requires a Mac-owned reset that stops the old bridge. A changed loopback Mac socket closes mobile routes instead of keeping open sockets with invalidated keys. The route announcement is a bootstrap hint, not a grant or substitute for v2 authentication. Both paths use the same pinned device keys and project policy; neither path can change account state.

The [iPhone connector](../../apps/MunieRemodex/App/Services/ManagedRelayPhoneConnector.swift) uses a bounded challenge and socket bootstrap on an explicit IPv4 loopback origin. It rejects redirects and passes the original owned socket and an untrusted session hint to the existing v2 handshake. The phone consults only the selected, pinned Mac and does not publish connected state until authenticated initialization. It ignores plaintext application messages and unauthenticated trust-state changes on the managed socket. The saved LAN address and session hint remain separate and unchanged on this path. LAN is tried first, and only a known transport reachability error permits this developer fallback; cancellation, denial and identity errors do not. See [loopback interoperability testing](../testing.md#managed-relay-loopback-interoperability).

Before enabling an endpoint, require ordinary TLS certificate validation, bounded requests and upgrades, admission and route replacement as one operation, and no public pairing or push routes. The per-role issuance budget is not a per-source request limiter: challenge requests are not authenticated yet, and a caller that knows a public key can compete for its budget. The hosted edge still needs separate source and service-wide limits. For comparison, [NGINX request limiting](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html) supports both scopes; no proxy or new dependency is selected here. Bind disable, disconnect and revocation to the correct sockets. Deactivation clears one registration; it does not prevent the allowlisted Mac from registering again, so the Mac adapter must stop registration on disable and only register currently trusted phones. Verify outage/fallback and replay with generated keys and no external account. Only then choose the hosting operator, service domain, capacity budget and minimal operational metadata retention. No deployment, cost commitment or credential access is part of the prototype.

Physical acceptance is separate: match the nearby codes on the actual Mac and iPhone, complete an authorized task and approval/cancellation, then reconnect the same thread over cellular with no VPN, return to LAN, and verify behavior after relay outage and revocation. Keep the control disabled in release until these gates pass.

An exhausted challenge issuance budget returns HTTP 429. The Debug iPhone keeps the reconnect intent and waits one issuance window before another attempt within its existing retry limits. A denied registration request remains HTTP 403 and does not trigger this retry path.

## Deployment review input

The first hosted pilot can use one always-on Linux instance and one reverse proxy on the same instance. Keep the managed relay listener on loopback and expose only the managed challenge POST and connect upgrade on a Munie-owned hostname. Do not forward LAN pairing, push, or account endpoints. Both apps use a fixed service origin and normal HTTPS/WSS hostname and chain validation; the operator cannot replace the v2 device identity. The Node process keeps routes in memory: do not add a second replica until registration ownership and reconnect semantics are shared, and test proxy reload and instance restart as outages rather than relying on connection persistence.

An owner-operated host and [Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) are a candidate, not new application dependencies. Caddy provides WebSocket proxying and [automatic HTTPS](https://caddyserver.com/docs/automatic-https); its [Apache-2.0 license](https://github.com/caddyserver/caddy/blob/master/LICENSE) applies if adopted. Its default configuration reload closes existing WebSockets, so the client must recover without replaying a turn. For iPhone, retain the platform's [standard URLSession trust evaluation](https://developer.apple.com/documentation/security/preventing-insecure-network-connections) rather than adding a certificate or cleartext exception.

Budget example checked on 2026-11-19: [Lightsail Linux with public IPv4](https://aws.amazon.com/lightsail/pricing/) lists USD 7/month for 1 GB of memory and a nominal 2 TB transfer allowance. [Allowances and overage rates vary by region](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-data-transfer-allowance.html); domain, snapshots, and operator effort are separate. This is not a capacity or billing guarantee. Before any spend, confirm the operator, hostname, region, capacity after load tests, and a monthly alert threshold. Retain only aggregate admission/availability and transfer counts by default; do not log payloads, keys, proof headers, or account data. No provider has been selected or provisioned.
