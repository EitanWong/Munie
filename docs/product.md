# Product and validated learning

## Promise and current scope

Munie aims to make a personal AI available with minimal effort across everyday Apple devices. Models and execution harnesses are replaceable. The first engineering slice is narrower: capture a short text, save reliably, find it later and delete it. Local capture is not an AI answer or an executed task.

First user: the owner, followed by a small invited cohort. First hypothesis: people repeatedly lose useful thoughts away from a desk, and an easier entry plus reliable retrieval changes that behavior. Compare with Notes, Siri/Shortcuts, Reminders and self-messaging before assuming a new app is needed.

The archived research supersedes the early Codex-specific fork idea: own the native frontend and data model; use Omi, Chums, OpenVision and Remodex as references for distinct mechanisms. A home Mac is an optional execution host, not a requirement for local capture.

## Build–Measure–Learn

Keep at most one main learning objective and one time-boxed technical investigation active. Fix the hypothesis, counter-evidence, measurement, threshold and time/cost budget before starting. Record observations separately from interpretation. Results can justify continuing, narrowing, changing the scenario, stopping, or keeping only a personal tool.

| Experiment | Method / provisional decision rule | Status |
|---|---|---|
| E1 Problem discovery | 12 qualified interviews; ≥8 repeated recent problems and ≥5 existing workarounds | Planned |
| E2 Transparent service prototype | 5 people × 7 days; ≥3 return on two later days and each uses a result | Planned |
| E3 Entry comparison | 8 paired users; median per-user time improvement ≥30%, without worse completion/quality | Planned |
| E4 First technical path | At most two developer days; cold start, lock, permission, interruption and network results | Planned |
| E5 Trust controls | 6 people; ≥5 can explain and operate relevant data/recording controls | Planned |
| E6 Invited activation/return | Rolling cohorts; define independent activation and full week-2 window before launch | Planned |
| E7 Payment | Real delivered value, one offer, actual purchases and refunds | Planned |
| E8 One acquisition channel | Contact → response → activation → return → payment, including founder time | Planned |

These are suggested internal rules from prior research, not market benchmarks. Founder use is a separate sample. Praise, downloads, simulated payment and AI-declared completion are not evidence of retained value. Invitations have not been sent by this project.

## Immediate execution

1. Set an affordable two-week time/cost cap and record 3–7 days of real triggers using the current method.
2. Pick one scenario. Start E1/E2 using the archived templates; use the capture app only where it helps learn.
3. Log anonymous event IDs, time, entry, success/failure, subsequent use and support minutes. Do not upload raw content by default.
4. Review evidence weekly. Add features only for an observed blocker or a necessary technical feasibility question.

The current app does not implement analytics. A diary or redacted local sheet is sufficient initially. Show numerator/denominator, preserve failures and prompted use, and report immature cohorts separately. Value for this slice means a saved item is later found **and used**, not merely that the app opened.

## Later technical gates

- Remote work: real cellular → authenticated gateway → awake home Mac → verifiable result; distinguish acceptance from completion and test duplicates, disconnection and cancellation.
- Watch: native interaction and pairing/background constraints; independent cellular use is a separate test.
- Displayless Ray-Ban Meta: validate current official SDK capabilities, device routing and distribution terms before product commitment.
- Voice/context: opt-in sessions first; interruptions, power, storage, retention, consent and incremental value before always-on sensing.
