# 轻量入口与远程 Agent 交互

状态：前期设计，2026-11-17。Munie 的核心目标是让用户在手机、Watch 等设备上随时发起、继续和管理自己 Mac 上的 Codex 工作；本机记录是离线草稿与输入保留的辅助能力。当前实现仍只有本机文本记录，远程任务、下表快捷入口及录音均未实现。证据见[入口调研](../../references/entry-point-research.md)，实际通过情况记入[项目状态](../project-status.md)。

## 一次明确的任务

核心路径为“触发 → 说出需求（手机可文字输入）→ Mac 上执行 → 主动摘要/必要时批准 → 结果提醒或语音回复 → 继续”。Watch 优先系统听写等原生语音输入和短任务，手机保留同等可用的文字路径；文本协议探针只是工程检查点，不是最终体验。首次配对完成后，常用设备默认使用用户上次明确选择的 Mac/工作区/任务；连接、模型和协议配置渐进披露。任务目标、运行状态、待批准后果和失败原因保持可感知。首次配对仍必须让用户确认主机与授权范围，不以减少步骤为由隐去权限。

每屏只有一个清楚的主任务，优先系统导航、输入与反馈。新任务和继续已有任务保持可区分，避免一句话误投另一工作区。常用入口直达任务输入或当前任务状态，不经过功能大厅。没有网络或 Mac 不可达时允许保留需求，但“已保存到本机”不能冒充“Mac 已接收”。当前内存草稿不会在进程退出后保留，只有显式保存的记录可重启找回。

| 入口 | 预期任务 / 最小交互 | 机制与限制 | 次序 |
|---|---|---|---|

## 入口共享任务语义

入口解析与导航留在 app/设备 adapter，远程协议模型与任务状态属于后续可测试领域层，Codex 进程和凭据归 Mac。只在真实第二调用者出现时抽包。具体网络拓扑、配对和安全协议必须先评审，不能把现有 `CaptureStore` 当远程任务协议。

第一片未来快捷入口限定为导航到“新任务输入 / 指定任务状态”，由 app 显示主机、工作区及真实状态，不在锁屏语音指令中直接批准或运行任意 shell。后续发送动作需要绑定用户、设备、主机、工作区与稳定 request ID，并记录真实接受事件；录音、AI 推测或前端动画都不能替代此事件。

本地离线输入仍经 `CaptureStore` 保存。`FileCaptureStore` 的 actor 只协调同一实例：同进程入口注入 app 的同一个 store。扩展最初只导航；若要求 widget/intent 后台写入，先有存储 ADR：App Group/entitlement、跨进程串行化或事务、数据保护、迁移与崩溃恢复。共享路径或 App Group 不自动协调文件写入，不能每个入口另造 actor 后声称安全。

导航仅携带允许的动作与不敏感 ID，验证路由和参数；不携带原文、密钥或任意命令。主机认证不等于任意工作区授权；任务提交不等于所有工具权限被批准。

## 可感知的状态

任务状态、可信升级依据、取消与不确定提交只在[远程 Agent 决策](../decisions/remote-agent-foundation.md#task-state-contract)维护。所有入口使用同一语义；界面采用本地化用户语言，不直接展示协议字段。

Mac 侧基于真实事件生成进度摘要、待审批与完成提醒，手机/Watch 按用户选择接收；合并重复事件并限制频次，避免逐 token 打扰。APNs 背景更新不保证投递，不能承诺即时或任意后台播报；app 再次打开时查询权威状态。关闭通知不阻塞手动查询；锁屏通知默认不带内容。音频回复只在用户同意的会话、合适路由和系统允许的状态下播放；短信是未来可选通道，需单独确认接收人、费用、隐私和服务部署，不能假装已经接通。无需看屏的入口也要区分成功、失败、需解锁与处理中，必要时使用系统对话/辅助反馈，提供查看详情路径。任何入口都不能因为界面简洁而默认扩大 Codex sandbox 或审批范围。

## 每个入口的准入验收

| 场景 | 必须观察到的结果 |
|---|---|
| 冷启动 / 前台 / 后台恢复 | 抵达正确主机和任务；新旧需求可区分，未发送输入不被覆盖 |
| 锁屏 / 首次解锁前 | 执行显式认证与数据保护策略；不泄露内容或接受未经认证的审批 |
| 蜂窝 → 互联网 → Mac / Wi-Fi 切换 | 真实非同局域网完成一项任务并找回结果；LAN 测试不能替代此证据 |
| Mac 睡眠 / 离线 / Codex 退出或登录过期 | 状态真实且可恢复；保留可恢复输入，不能假称唤醒或运行 |
| 配对过期 / 设备撤销 / 错误设备 | 拒绝新请求和失效审批；不回传 Codex 凭据 |
| 重复提交 / 乱序重放 / 超时 / 取消 | 使用稳定 request ID 与事件序号去重；核对不确定提交，禁止盲重放副作用；审批绑定正确请求，覆盖上游提交后崩溃窗口 |
| 通知拒绝 / Focus / 延迟投递 / 重复完成事件 | 手动查询可用，重连补齐权威状态；不重复播报或误称即时触达 |
| 拒绝/撤销麦克风、电话中断、蓝牙切换 | 文本路径继续；录音真实停止并更新状态，不静默恢复采集 |
| English / 简体中文 / VoiceOver / 大字 | 目标、审批后果、错误和结果可理解；主动作可达，焦点与返回上下文可恢复 |
| 耗时 / 能耗 / 后台限制 | 分开记录入口反馈、网络接受、首个事件及完成时间；按[性能规范](performance.md)测量，Mac 存储基准不能代替远程/Watch 体验 |

图片、照片、视频和相机是未来任务输入，统一关联任务并保留来源/权限/取消语义；上传与实时流的具体边界由媒体方案评审。长期可评估 Qwen 等语音协调器及眼镜现场上下文，让语音层路由到 Codex 等执行 Agent；模型选择不直接授予设备、工作区或工具权限，持续采集须是显式可结束的会话。

每次只增加一个可验证入口，先证明语音发起/继续/审批/结果闭环，再铺开设备。用[产品实验](../product.md)比较当前回到 Mac 使用 Codex 的方式，观察任务完成率、操作步骤和等待感；实际改善需测量，不由文档宣告。

## 硬件触发与掌控感

硬件 API 与系统支持证据唯一记录于[入口研究的硬件段](../../references/entry-point-research.md#apple-硬件入口与反馈复核)。iPhone/Watch 按键优先用户选择的系统 Shortcut，AirPods 优先 Siri→任务 intent。按下后清楚反馈“开始听/已停止/提交中/主机已接收”，不能让用户猜是否录到或是否真的执行。耳机上的 intent 返回简短 dialog；长任务后续结果通过通知或已允许的会话回报，不能一直阻塞 Siri 等待完整执行。

反馈路由区分 Mac 已完成、通知已排队/送达、用户已看到/听到；每个任务按事件去重。用户选择仅耳机播报时，摘下耳机、切到车载/扬声器或通话中断应停止私密朗读并保留通知/手动查询，不自动外放。手机与 Watch 的提示、音量/静音、Focus 和播报偏好统一解释，避免同时在三处重复朗读；任何必要审批都有可理解、可拒绝的路径。

设备验收必须记录具体 iPhone/Watch/AirPods 型号、OS/固件、连接到哪台设备、按键/Shortcut 配置、语言、锁屏/前后台、通知/Siri/播报设置和失败分母。分别运行“按下→说话→Mac实际接受→真实进度→完成→正确设备反馈”，加入蓝牙切换、戴/摘、通话、Focus、撤权与离线。以测量确认及时性，不承诺系统未保证的即刻送达或后台全局按键监听。

所有设备共享用户目标、当前任务和授权语义；具体交互由设备决定。采用前台快速入口、按需展开和明确设备接续，避免让用户学习平台/模型/协议差异。跨设备任务接续需实现受认证状态同步后才能宣称可用；共享 Swift 源码本身不带来接续。平台构建与运行记录统一见[平台验收](platform-acceptance.md)，不在每种入口再维护另一份状态。
